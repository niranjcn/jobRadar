# Subscription Model Plan — Multi-user, Coupons, Privileged Users, Faster Matching, Admin

> Status: **Phases 1–6 implemented (backend + frontend); auth enforcement is ON.**
> Migrations 022–026 applied; per-source fast matching + notification queue live;
> `SECRET_KEY` generated, `JOBQUEST_REQUIRE_AUTH=true` and
> `SESSION_COOKIE_SECURE=true` are set in `.env` — anonymous API access is
> closed, login is via email OTP (owner) / Telegram initData (once linked), and
> locked accounts see only the unlock path. Frontend: login / register /
> unlock / pricing / onboarding / billing pages plus the full `/admin` area.
> Both access modes smoke-tested end-to-end against the live database.
> Remaining: a real payment provider (Phase 7) — the `manual` backend and
> coupon flow cover everything until then. See §15 for phase detail.
> Extends `docs/auth-multi-user-plan.md` (users/auth/notification queue) with an
> access layer (payment **or** coupon), privileged accounts, per-user delays,
> and preference presets. Each phase is independently testable and must not break
> the running single-user system.

## 1. Goals

1. Convert JobQuest from single-user to a **subscription SaaS**.
2. **Make matching faster**: today every job waits for *all* sources in a poll run
   to finish before matching + notifying. New jobs must match and enqueue alerts
   **per-source, immediately** after ingestion.
3. **Admin page**: manage users, revoke/grant permissions, promote to
   **privileged**, set **per-user alert delays**, generate **coupon codes**, and
   manage **preference presets**.
4. **Access model**: a new registrant unlocks the product by either
   (a) paying a subscription, or (b) redeeming a **single-use, 12-hour-valid
   coupon** generated by admin (regular or privileged flavor).
5. **Privileged users** (friends & family): see all jobs like the admin, filtered
   by their own preferences — with an admin-controlled delivery delay per user
   (e.g., 10 minutes behind admin).
6. **Preference presets**: reusable preference bundles ("Entry Level Software
   Engineer", …). The existing live configuration is preserved forever as the
   admin-only preset **"Admin Preference"**. Current preference data is not changed.
7. Define **registration flow** and **what each account type sees**.

## 2. Constraints & guardrails

- **Preferences are frozen**: no column changes to `preferences`, no data
  migration of preference rows. Only a non-destructive FK is added (§9).
  Presets are a *new* table; applying a preset writes a *user's* row through the
  normal save path — the seeded "Admin Preference" preset is a **copy** of the
  current config, and the original row keeps working untouched.
- Jobs remain **global/shared storage** (one ingest serves all users) — only
  `job_matches`, notifications, and access state are per-user.
- No Redis/Celery/Kafka. Queues live in Postgres (AGENTS.md §3) until profiling
  says otherwise.
- No AI on any critical path (deterministic matching stays the engine).
- Migrations continue the hand-rolled runner (`backend/app/migrate.py`); next
  number is **022** (highest today: `021_google_amazon_ats.sql`).
- Auth debt must be fixed first: every endpoint is currently unauthenticated
  (`ARCHITECTURE_REVIEW.md` C1). You cannot sell access to an open API.

## 4. Decision log (lock these first)

| # | Decision | Rationale |
|---|---|---|
| D1 | Adopt the auth plan's `users` table + OTP/initData auth (its D1–D11 carry over). | Avoid two competing identity designs. |
| D2 | Sentinel user becomes the **owner/admin** account. All existing rows keep working. | Zero data migration; satisfies "don't touch preference data". |
| D3 | Account types are a `role` column: **`user` \| `privileged` \| `admin`**, plus the auth plan's `capabilities text[]` for **fine-grained revocation** on top. Role = what you are; capabilities = what admin has individually switched off/on. | "Make him privileged" and "revoke his permission" are two different operations; model both directly. |
| D4 | **Per-user delay** lives on the user: `alert_delay_minutes int` (admin-settable). Alerts are enqueued with `scheduled_for = now() + delay`; the drain worker delivers when due. | Exactly implements "this user sees postings 10 min late"; free with the notification queue (D6). Admin defaults to 0. |
| D5 | **Coupons** are admin-generated, **single-use** (one claimant, enforced in DB) and expire **12 hours after creation** (server-enforced, non-negotiable constant). Two flavors: `user` (standard access) and `privileged` (privileged role). | Spec'd by owner; the DB makes cheating impossible rather than trusting UI. |
| D6 | Alerts always go through `notification_queue`; per-user `alert_delay_minutes` decides `scheduled_for`. Drain worker sends due items every ~30 s. | One mechanism delivers "fast" (delay 0) and "delayed" (any N minutes). |
| D7 | Matching moves **inside the per-source task** (`_poll` in `poller.py`), not after `gather()`. | Kills the biggest latency: one slow board no longer delays 126 others' matches. |
| D8 | Matcher evaluates candidates against **all eligible users' preferences loaded once per run**, not per-call. | O(jobs × users) substring checks are cheap; avoids N round-trips. |
| D9 | Access = **paid subscription OR redeemed coupon OR admin grant**. There is **no free tier**: registered-but-unlocked accounts hit a lock screen offering Pay / Enter coupon. | Matches owner spec; coupons double as the invite/waitlist mechanism. |
| D10 | Entitlement resolution lives in one service (`app/services/entitlements.py`) merging role defaults ∪ capabilities ∪ subscription state; short TTL cache. | Single source of truth consumed by routes, matcher, drain worker, `/api/me`, frontend. |
| D11 | System pages (sources, schedule, runs, location-mapping settings, companies edit) move behind `admin`. | Operator tools, not subscriber features. |
| D12 | Plan limits enforce at the **write-validation layer** (`PUT /api/preferences`), never by mutating stored preference data. | Respects the freeze constraint; revocation doesn't destroy data. |
| D13 | **Preference presets** are rows in a new `preference_presets` table; "Admin Preference" is seeded as a copy of today's live config with `is_admin_only=true`. Applying a preset copies values into the target user's `preferences` row and triggers the normal recompute. | Reusable bundles per owner spec; original data preserved verbatim. |
| D14 | Webhook/billing events persisted raw (`billing_events`) and processed idempotently. Payment provider abstracted behind a thin adapter shipping with a **manual** backend first. | Card payments can be wired whenever the owner picks a provider (§5); everything else works day one. |

## 5. Subscription method analysis (which provider?)

| Criterion | **Stripe Billing** | **Paddle** | **Lemon Squeezy** | **Razorpay** | Manual (UPI/transfer) |
|---|---|---|---|---|---|
| Merchant of Record (handles global VAT/GST, invoices) | ✗ (you are) | ✓ | ✓ | ✗ (you are) | ✗ |
| Works for solo dev **without** a registered company | Painful in many countries | ✓ | ✓ | Partially (India KYC for individuals) | ✓ |
| Card support | ✓ | ✓ | ✓ | ✓ (+UPI/netbanking) | manual |
| Hosted checkout + customer portal | ✓ (excellent) | ✓ | ✓ | ✓ | none |
| Webhooks / idempotency | ✓ mature | ✓ | ✓ | ✓ | n/a |
| Payouts to India | Limited/hard | ✓ (wire) | ✓ | ✓ native | direct |
| Integration effort | Medium | Low | Low | Medium | trivial but doesn't scale |
| Fees | ~2.9%+ | ~5% | ~5%+ | ~2–3% | 0% |

**Recommendation**

- **No registered company / solo** → **Lemon Squeezy or Paddle** (merchant of
  record absorbs global tax compliance — usually worth the fee for one person).
- **Registered entity, non-India** → **Stripe** (cheapest, hosted Checkout +
  Billing portals minimize UI work).
- **India-based customers primarily** → consider **Razorpay** (UPI adoption),
  accepting you handle GST invoicing yourself.
- Regardless: ship with `BILLING_PROVIDER=manual` first — admin marks payments
  received by hand — then flip config to the real provider. Coupons cover
  everyone who shouldn't pay.

Schema stays provider-neutral (`subscriptions.provider` +
generic ids + raw `billing_events`). **Owner decision needed:** jurisdiction/entity
(§20).

## 6. Registration & access flow

```text
Register (email → OTP via Resend;  or Telegram /start → initData HMAC)
        ↓
Account created (role='user', NO access yet) → Lock screen:
        ┌────────────────────────────────────────────┐
        │  Unlock JobQuest                           │
        │  [ Subscribe — ₹/$ per month ]             │
        │  [ Have a coupon? Paste it here ]          │
        └────────────────────────────────────────────┘
        ↓                                    ↓
  payment success                     POST /api/coupons/redeem {code}
  (webhook flips access)              ✓ unclaimed · unexpired(≤12h) · correct shape
        ↓                                    ↓
        └────────────── access granted ──────┘
                         ↓
   role = 'user' (paid/coupon)  or  'privileged' (privileged coupon / admin action)
   subscription row provisioned (provider = stripe|paddle|…|coupon|manual)
                         ↓
   Onboarding: pick/enter preferences (existing UI, untouched schema)
                         ↓
   Connect Telegram (deep-link + 6-digit ownership code) → alerts at (now + user.delay)
```

Rules:

- Registration alone never grants product access (D9) — this is also the spam
  brake, replacing the old approval-gate idea.
- Coupon redemption is atomic: `update coupon_codes set claimed_by=$me,
  claimed_at=now() where code=$c and claimed_by is null and expires_at > now()`
  — zero-row result ⇒ reject (already claimed/expired). Race-proof.
- Expired/used coupon → clear error, no partial state.
- Admin can bypass everything: grant/revoke access, flip roles, set delays from
  `/admin` (or bot commands).

## 7. Accounts, entitlements & delays

### Account types

| | **user** (paid / basic coupon) | **privileged** (friends & family) | **admin** (you) |
|---|---|---|---|
| Dashboard, jobs, matches, notifications | ✓ | ✓ (identical breadth to admin) | ✓ |
| Own preferences | ✓ | ✓ | ✓ (current config preserved as-is) |
| Email + Telegram alerts | ✓ | ✓ | ✓ |
| Alert timing | instant by default (admin may set delay) | **admin-set per-user delay** (minutes; 0 = instant) | instant (delay forced 0 recommended) |
| Match history | full | full | full |
| Preference presets assignable by admin | ✓ | ✓ | ✓ |
| Sources / schedule / runs / settings / companies edit | – | – | ✓ |
| `/admin` pages, coupons, roles, delays | – | – | ✓ |
| Fine-grained revocation | via `capabilities` | via `capabilities` | n/a |

### Entitlement merge order (D10)

```text
effective = role_defaults(role)          # user | privileged | admin
          ∪ capabilities                 # admin per-user overrides (grant OR revoke)
          ∧ subscription_active(user)    # user role only; privileged/admin exempt
```

### Delays

One integer governs everything: `users.alert_delay_minutes`.
Queue inserts compute `scheduled_for = now() + alert_delay_minutes`; the drain
worker releases them when due. Setting 10 in `/admin/users/{id}` literally means
"this human sees each posting 10 minutes after the admin". Changing the value
affects future queue inserts only (already-scheduled sends stand) — simple,
predictable, documented behavior.

### Pricing placeholder

Single paid plan **Standard** (~$9/mo or ₹749/mo — owner confirms §20).
More tiers can be added later by inserting `plans` rows; nothing in the schema
assumes exactly one paid plan.

## 10. Faster matching — target architecture

### Problem (measured from code)
`poll_all_sources` (`poller.py:428-582`):
1. Gathers up to 127 source polls concurrently (semaphore 8).
2. **Waits for every one** (`gather`, :500).
3. Then `match_all` (:503) → then Telegram send (:520) → then email send (:537).

A single slow board (Workday timeouts, retries) delays *every* user's matches
and alerts by the tail latency of the worst source.

### Target flow
```text
per source task (_poll):
   fetch → normalize → upsert
        ↓ immediately, per source:
   match candidates against all eligible users' prefs (in memory)
   upsert job_matches
   insert notification_queue rows (scheduled_for = now + users.alert_delay_minutes)
        ↓
drain worker (scheduler tick, ~30s):
   select due rows → group by (user, channel) → send → mark sent / retry / fail
```

### Implementation stages

**S1 — Move matching into the per-source task (core fix, small diff)**
- Hoist preference loading above the gather loop: new `load_all_user_preferences(supabase)` returns prefs for every unlocked, non-disabled user, once per run (D8).
- Inside `_poll`, after `poll_source` returns `new_ids`: call
  `match_and_enqueue(supabase, jobs=<in-memory NormalizedJob objects>, prefs=all_prefs, geo=...)`.
  Pass objects straight through — kills the post-hoc `fetch_candidate_jobs`
  refetch (`poller.py:517`) entirely.
- Delete the block-level `match_all`/send calls; `finish_poll_run` aggregates counters via a concurrency-safe tally.
- Preserve `notify_first_check` semantics exactly.
- Result: match latency per job ≈ its own source's fetch time; matching overlaps remaining fetches.

**S2 — Queue-driven delivery (§9/023)**
- Replace inline `send_telegram_notifications`/`send_email_notifications` calls with queue inserts; `drain_notification_queue()` piggybacked on the existing APScheduler (30 s ticker).
- `scheduled_for = now() + users.alert_delay_minutes` implements admin-set delays and "privileged 10 min behind admin" natively.
- Failure policy: `attempts+1` with backoff, `failed` after 3; FK cascade cancels rows for pruned jobs.

**S3 — Optional: decouple ingest from match via a Postgres match queue**
Only if profiling ever makes synchronous per-source matching the bottleneck
(unlikely below ~1k users × ~2k jobs/run). Design ready:
`match_queue(job_id)` filled on upsert, consumers use `FOR UPDATE SKIP LOCKED`.
Do **not** build now (AGENTS.md: no infra without demonstrated need).

**Matcher internals stay untouched** — `job_matches_preferences` /
`compute_match_score` (`matcher.py:27-143`) and SQL `recompute_job_matches`
(preference-save path) are correct; only orchestration moves.

### Expected effect

| Metric | Today | After S1+S2 |
|---|---|---|
| Job → matched | end of whole run (worst-case minutes) | ≤ its source's fetch time |
| Matched → alerted | after match + sequential sends | ≤ drain interval (~30 s) + user's configured delay |
| One hung source blocks others | yes | no |
| Sends retryable | no (inline fire-and-forget) | yes (queue, 3 attempts) |

## 11. Access & billing flows

```text
Coupon:   admin clicks Generate → picks flavor (user|privileged) [+ duration_days, note]
          → server mints code, expires_at = now() + 12 h (hard cap)
          → admin shares code out-of-band (WhatsApp etc.)
Redeem:   POST /api/coupons/redeem {code}   (authenticated, locked account)
          → atomic claim (unclaimed ∧ unexpired) → set role per grants_role,
            lift access_locked, provision subscription(provider='coupon',
            period_end = now()+duration_days or null)
Payment:  Lock screen → POST /api/billing/checkout {plan_code:'standard'}
          → provider adapter (manual: 'pay admin, he flips the switch'; real PSP later)
          → signed webhook → billing_events (idempotent) → access unlocked
Portal:   GET /api/billing/portal → provider-hosted manage/cancel/invoices (PSP mode)
Expiry:   daily sweep: expired subscriptions (period_end passed) → status='expired',
          access_locked=true again (preferences/data retained — just locked out)
Revoke:   admin disable/lock instantly overrides everything (status='disabled' wins)
Comp:     admin PUT /api/admin/users/{id}/subscription — same machinery, provider='manual'
```

Provider adapter interface (`app/billing/provider.py`):
`create_checkout(user, plan, return_url)`, `create_portal_url(user)`,
`verify_webhook(raw_body, headers) -> WebhookEvent`, `map_event(evt) -> AccessUpdate | None`.

## 16. Testing strategy

- **Unit (pytest, fixture-based, offline)**: entitlement merge (role ∪ capabilities ∧ subscription), coupon lifecycle (mint→12 h expiry boundary, atomic double-claim race, wrong-flavor effects), delay math (`scheduled_for` correctness, mid-flight delay change semantics), preset apply fidelity, expiry sweep, `has_cap` matrix, queue retry→failed.
- **Poller regression**: assert per-source match invocation ordering (source A matched while B still fetching — futures/timers); parity test proving `match_and_enqueue` output equals legacy `match_all` on a fixed candidate set.
- **Matcher**: unchanged logic covered by existing tests.
- **API suite**: 401/402/403 matrix (anon / locked / user / privileged / disabled / admin); coupon race (two concurrent redeems ⇒ exactly one winner); admin-route denial; webhook signature rejection + replay-idempotency.
- **Frontend (vitest)**: guard redirects (incl. locked → `/unlock`), role-gated rendering, coupon box validation states.
- **Live smoke**: owner + friend's phone: mint privileged coupon → redeem within 12 h → friend's alerts arrive exactly `delay` behind owner's for the same job; second redemption attempt fails; expired code fails.

## 17. Security checklist

- Coupon entropy ≥ 16 chars, constant-time lookup, brute-force rate limit on redeem (per IP + account), failed attempts logged (never the codes themselves).
- Atomic DB claim (conditional UPDATE) — no read-then-write races.
- Signature-verified webhooks only (raw body, constant-time compare); events persisted before processing; client can never assert entitlement — server derives from DB only.
- Session cookies httpOnly / SameSite=Lax / Secure-in-prod; OTP codes single-use, 5-min, attempt-capped, rate-limited.
- Admin dependency on every `/api/admin/*` and relocated system route (fixes ARCHITECTURE_REVIEW C1 alongside Phase 1).
- Secrets via env only; `BILLING_*` keys in `.env.example` as placeholders.

## 18. Definition of done

- Migrations 022–025 apply cleanly on fresh **and** existing DBs; zero preference-data change (row checksum before/after in migration test); "Admin Preference" preset equals the original row at seed time.
- Every route authenticated; non-admin cannot reach system routes; locked accounts reach only the unlock path.
- Per-source matching live; latency targets of §10 met in staging; per-user delays honored end-to-end.
- Coupons are provably single-use and dead after 12 h (DB constraints + tests).
- Admin can manage users, roles, delays, capabilities, coupons, and presets from web (bot parity where listed).
- Ruff clean, pytest green, vitest green, CI passing.
